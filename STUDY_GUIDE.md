## Как устроено приложение

`uvicorn app.main:app` загружает объект `app` из `app/main.py`. Перед ним выполняется `alembic upgrade head`, чтобы создать актуальную схему. При запуске `lifespan` проверяет WEBHOOK_SECRET, сохраняет его в app.state, вызывает `setup_database` и сохраняет фабрику сессий. При остановке соединения закрываются через `engine.dispose()`. Таблицы создают миграции; приложение только добавляет тарифы basic/standard/premium с фиксированными ID. Повторный запуск не дублирует их. Без секретного ключа запуск завершается с понятной ошибкой.

`Tariff` и `Payment` — ORM-модели: они описывают таблицы, столбцы, внешний ключ и связь. Один тариф может иметь много платежей; каждый платёж относится к одному тарифу через `tariff_id`. `Payment.schedule` хранит список целых сумм в JSON-столбце, а для обычного платежа содержит `null`. `idempotency_key` имеет ограничение уникальности в БД, чтобы повторный ключ не создавал второй платёж даже при конкурентных запросах. `created_at` заполняется текущим временем UTC.

Функция `get_session` выдаёт отдельную SQLAlchemy-сессию на запрос через `Depends(get_session)`. После запроса контекстный менеджер закрывает её. Сессия отслеживает объекты и сохраняет изменения при `commit`. SQLAlchemy и обработчики с БД синхронные; FastAPI выполняет их в пуле потоков. Проверка HMAC асинхронная, потому что читает HTTP-тело через `await request.body()`. Это не превращает сессии БД в асинхронные.

Pydantic-схемы отделены от ORM-моделей. `PaymentCreate` и `BankWebhook` проверяют входные данные, `PaymentOut` и `TariffOut` задают точный формат ответа. `HealthOut` описывает успешную проверку доступности с полем `status: Literal["ok"]`. `ConfigDict(from_attributes=True)` разрешает Pydantic читать атрибуты ORM-объекта. `EmailStr` проверяет адрес; `Literal[3, 6, 12]` ограничивает сроки; `PaymentMethod` и `PaymentStatus` ограничивают строковые значения. Валидатор `promo_code` допускает только `KVITTO10` без учёта регистра. `model_validator` требует срок только для рассрочки. Неверный запрос автоматически получает стандартный FastAPI `422` с полем `detail`.

## Endpoint и функции `app/main.py`

| Функция / маршрут | Что делает | Успех и ошибки |
| --- | --- | --- |
| `list_tariffs`, `GET /tariffs` | Выбирает тарифы в порядке ID. | `200`, список `{id,title,price}`. |
| `create_payment`, `POST /payments` | Проверяет ключ повтора, ищет тариф, вычисляет скидку и график, сохраняет платёж. | `201` для нового, `200` для повтора, `404` без тарифа, `422` для некорректных данных. |
| `get_payment`, `GET /payments/{payment_id}` | Находит платёж по ID. | `200` с полями платежа или `404`. |
| `list_payments`, `GET /payments` | Читает список по ID, добавляет WHERE по email/status при наличии фильтров. Оба условия объединяются AND. | `200`, список или []; `422` для невалидных фильтров. |
| `refund_payment`, `POST /payments/{payment_id}/refund` | Без тела запроса переводит succeeded в refunded, возвращает обновлённый платёж. | `200`, `404`, `409` при другом статусе, `422` при нечисловом ID. |
| `bank_webhook`, `POST /webhooks/bank` | Сначала проверяет подпись через dependency, затем платёж и переход. | `200 {"result":"ok"}`, `401` для подписи, `404`, `409 {"error":"invalid_transition"}`, `422` для невалидного тела. |
| `health`, `GET /health` | Выполняет SELECT 1 через сессию БД. | `200 {"status":"ok"}`; при SQLAlchemyError — rollback и `503 {"detail":"database unavailable"}`. |

Новый платёж имеет `pending`. Разрешены только `pending → succeeded`, `pending → failed`, `succeeded → refunded`. Таблица `ALLOWED_TRANSITIONS` делает правила видимыми. При запрещённом переходе `commit` не вызывается и статус не меняется.

### Подпись банка и конфигурация

`verify_bank_signature` подключён через `dependencies=[Depends(verify_bank_signature)]`. FastAPI получает X-Signature из заголовка. `await request.body()` возвращает исходные байты; тело нельзя повторно сериализовать для проверки, потому что пробелы изменяют подпись. Проверка выполняет:

```python
expected = hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
```

HMAC — контроль целостности и подтверждение знания общего секрета, а не шифрование тела. `compare_digest` сравнивает подписи с защитой от утечки по времени сравнения. Неверная или отсутствующая подпись даёт 401 и не меняет платёж. Здесь подписывается JSON с lowercase hex digest без префикса. Для вызова банка нужен тот же WEBHOOK_SECRET, что использует API.

Фильтры GET /payments объявлены через Query. EmailStr проверяет email, PaymentStatus проверяет название статуса. Если фильтр отсутствует, соответствующий WHERE не добавляется. Это простая выборка без дополнительных слоёв.

### Одновременные вебхуки и внешние ключи

Проверить статус после чтения недостаточно: другой запрос может изменить его до сохранения. Поэтому общая функция `transition_payment_status(payment, target, session)` проверяет правила и выполняет условный SQL UPDATE. Её вызывают вебхук и рефанд:

```python
statement = (
    update(Payment)
    .where(Payment.id == payment.id, Payment.status == payment.status)
    .values(status=target)
)
```

База изменит запись только если статус всё ещё равен прочитанному. `result.rowcount` показывает число изменённых строк. Если оно равно нулю, другой запрос уже изменил статус: вызывается `rollback`, функция возвращает False и endpoint отвечает 409. При успехе функция делает commit и возвращает True. `synchronize_session=False` отключает обновление загруженного ORM-объекта в памяти. Вебхук возвращает только результат; рефанд вызывает `session.refresh(payment)` перед ответом, чтобы вернуть актуальный refunded. Правило и запись проверяются атомарно в БД, а не двумя независимыми действиями Python.

В `app/db.py` вложенная функция `enable_foreign_keys` подключена через `@event.listens_for(engine, "connect")`. Она выполняет `PRAGMA foreign_keys=ON` для каждого нового SQLite-соединения. Одного объявления ForeignKey в модели недостаточно: SQLite по умолчанию может не проверять его. Теперь платёж с несуществующим тарифом невозможно записать и напрямую через ORM. Закрытие engine помещено в `finally` lifespan: освобождение соединений выполняется и при исключении.

### Денежные расчёты

Тарифная цена, `discount`, `amount` и части графика — целые копейки; `float` не используется. Промокод даёт `price // 10` скидки. У заданных трёх цен 10% выражается целым числом копеек. `amount = price - discount` — сумма после скидки.

Для рассрочки используется:

```python
each, remainder = divmod(amount, data.installment_months)
schedule = [each + (index < remainder) for index in range(data.installment_months)]
```

`divmod` возвращает целую часть и остаток. В Python `True` в арифметике равен `1`: первые `remainder` платежей получают по одной дополнительной копейке. Поэтому сумма графика всегда равна `amount`. Например, 1 990 000 копеек на три месяца дают `[663334, 663333, 663333]`.

### Повторные запросы и ошибки БД

При `Idempotency-Key` сначала ищется существующий платёж. Если он найден, ответ `200` содержит его данные. Для нового платежа уникальность ключа дополнительно обеспечивает БД. Если два запроса одновременно не нашли ключ и один успел сохранить запись первым, второй получает `IntegrityError`, откатывает свою транзакцию, читает уже созданный платёж и возвращает `200`. Ошибка другого типа не маскируется. При отсутствии ключа каждый запрос создаёт новый платёж.

`HTTPException(404)` используется для отсутствующих сущностей. Для точного тела ошибки перехода `{"error":"invalid_transition"}` вебхук сам выставляет 409 и возвращает словарь; рефанд возвращает JSONResponse с кодом 409. JSONResponse позволяет вернуть ошибку, не пропуская её через схему успешного PaymentOut. Обычный HTTPException использовал бы поле detail. У health ошибка доступа к БД обрабатывается через HTTPException(503); внутреннее сообщение ошибки не выдаётся клиенту.

## Тесты

Фикстура `client` в `tests/conftest.py` задаёт уникальный путь SQLite через tmp_path, применяет настоящую миграцию, задаёт фиктивный WEBHOOK_SECRET и запускает lifespan внутри TestClient. HTTPX request-hook подписывает исходные байты банковских запросов, если подпись не задана явно. В тестах отсутствующей подписи hook отключается. monkeypatch возвращает прежнее окружение после теста. Функция payload в test_api.py собирает валидный запрос и позволяет менять только нужные поля.

Тесты проверяют точные цены, скидку и нижний регистр промокода, поля ответа, график для 3/6/12 месяцев, повтор ключа без второго платежа, ошибки 422 и 404, полный путь статусов и сохранение прежнего статуса после 409. `@pytest.mark.parametrize` запускает один тест графика с тремя сроками. Тестируется HTTP-поведение через httpx/TestClient, а не прямой вызов функций.

`test_all_status_transitions` проверяет все 16 пар статусов. `test_concurrent_webhooks_allow_only_one_transition` запускает два HTTP-запроса в `ThreadPoolExecutor`. `Barrier(2)` в обработчике ORM-события load заставляет оба запроса прочитать исходный статус до записи: так тест надёжно воспроизводит гонку. Обработчик события снимается в `finally`. Ожидаются один 200, один 409 и финальный статус победившего запроса. `test_database_rejects_missing_tariff` отдельно работает через ORM и проверяет `IntegrityError` при нарушении внешнего ключа; после ошибки нужен `rollback`.

Тесты рефанда проверяют succeeded → refunded с сохранением всех денежных полей, запрет из pending/failed/refunded, отсутствующий и нечисловой ID. `test_concurrent_refunds_allow_only_one_transition` проверяет гонку двух рефандов и рефанда с банковским уведомлением о возврате. Health проверяется с рабочей БД и с искусственно вызванным OperationalError: ожидается 503.

В test_bonuses.py проверены фильтры по отдельности/вместе, пустая выборка, 422, отсутствие/неверная подпись и изменение одного байта тела. Тест миграций выполняет upgrade дважды, check без расхождений с ORM, downgrade на временной БД и повторный upgrade. Всего pytest выполняет 47 проверок с учётом параметризации.

## Миграции, Docker и CI

Alembic хранит применённую ревизию в alembic_version. `upgrade head` выполняет отсутствующие миграции по цепочке down_revision. В 0001 создаются таблицы и ограничения; старт API отдельно добавляет тарифы. `alembic check` сравнивает ORM metadata со схемой. `downgrade base` удаляет таблицы, поэтому его используют только на временной БД. Раннюю существующую схему этого проекта можно отметить stamp 0001 после проверки и резервной копии: stamp не выполняет SQL изменения.

Dockerfile копирует приложение, миграции и конфигурацию, устанавливает зависимости, а CMD сначала выполняет upgrade, затем запускает Uvicorn. `exec` передаёт управление Uvicorn, чтобы он получал сигналы остановки. Compose монтирует payments_data в /data и сохраняет SQLite после рестарта. .dockerignore исключает .env, локальную БД и кэши. Healthcheck выполняет GET /health.

CI имеет один последовательный job: устанавливает Python 3.11, запускает Ruff и pytest, затем собирает контейнер, ждёт healthcheck, вызывает smoke_api.py и проверяет данные после рестарта. Секрет генерируется на один CI-запуск. Cleanup удаляет только временный CI-volume. AGENTS.md задаёт правила будущим сессиям Codex, но выполнение тестов подтверждается командами и CI.

## Возможные вопросы на техническом собеседовании

1. **Почему FastAPI?** Он быстро позволяет описать HTTP API, проверяет Pydantic-модели и создаёт документацию OpenAPI.
2. **Что такое endpoint?** Обработчик конкретной пары HTTP-метод и путь, например `POST /payments`.
3. **Что показывает GET /health?** Приложение отвечает и может выполнить SELECT 1 в БД. Успех — 200, ошибка БД — 503.
4. **Почему создание возвращает 201?** Ресурс создан; при повторе уже существующего платежа возвращается 200.
5. **Что делает `Depends`?** FastAPI вызывает указанную зависимость и передаёт её результат обработчику.
6. **Как работает dependency injection здесь?** `get_session` создаёт сессию для запроса, endpoint получает её параметром, после запроса сессия закрывается.
7. **Зачем Pydantic-схемы?** Проверять вход и контролировать поля выхода независимо от устройства таблиц.
8. **Чем ORM-модель отличается от Pydantic-модели?** ORM отображает строку таблицы, Pydantic описывает и валидирует данные API.
9. **Зачем `from_attributes=True`?** Чтобы схема ответа читала поля ORM-объекта по атрибутам.
10. **Почему суммы целые?** Двоичные числа с плавающей точкой могут неточно представлять десятичные дроби; копейки в `int` точны.
11. **Что означает `discount`?** Сколько копеек вычтено из цены тарифа; `amount` — итоговая сумма.
12. **Как вызывается возврат?** POST /payments/{id}/refund без тела запроса. Только succeeded переводится в refunded; другой статус даёт 409, неизвестный платёж — 404. Реального банковского вызова в тестовом нет.
13. **Зачем `Literal[3,6,12]`?** Он отклоняет другие сроки до выполнения бизнес-логики.
14. **Почему используется `model_validator`?** Правило о сроке зависит сразу от двух полей: метода и числа месяцев.
15. **Как работает промокод без учёта регистра?** Проверяем `value.upper() == "KVITTO10"`.
16. **Как связаны таблицы?** `Payment.tariff_id` — внешний ключ на `Tariff.id`; один тариф связан со многими платежами. Для фактического контроля SQLite включён foreign_keys на каждом соединении.
17. **Что такое сессия SQLAlchemy?** Объект для запросов и транзакций БД, который отслеживает изменения ORM-объектов.
18. **Когда вызывается `commit`?** После создания платежа или разрешённого обновления статуса; 409 ничего не сохраняет.
19. **Что такое идемпотентность здесь?** Один и тот же ключ возвращает один уже созданный платёж, не создавая дубль.
20. **Как защищены конкурентные запросы?** При создании платежа — уникальным ключом в БД и обработкой IntegrityError. При вебхуке и рефанде — общим условным UPDATE по ID и исходному статусу, с 409 при нулевом rowcount.
21. **Почему 404, 409 и 422?** 404 — сущности нет, 409 — конфликт перехода с текущим статусом, 422 — тело запроса не прошло проверку.
22. **Почему для 409 не применён `HTTPException`?** Нужно точное поле `error`; стандартное исключение использует `detail`.
23. **Какие edge cases учтены?** Неизвестный промокод, неверный срок, отсутствующие записи, повтор ключа, запрещённые переходы, остаток копеек.
24. **Как тестируются endpoint?** `TestClient` отправляет HTTP-запросы к приложению с отдельной временной БД и проверяет ответы и сохранённое состояние.
25. **Зачем фикстура `client`?** Она готовит чистую БД для каждого теста и запускает код старта приложения.
26. **Где используется async/await?** В dependency подписи для чтения Request.body. SQLAlchemy и endpoint с БД остаются синхронными и выполняются в пуле потоков FastAPI.
27. **Как меняется конфигурация БД?** Через `DATABASE_URL`; без неё берётся локальный SQLite-файл.
28. **Что делает Alembic?** Меняет схему по версиям. upgrade head создаёт нужные таблицы, current показывает ревизию, check проверяет соответствие ORM. Повтор upgrade ничего не дублирует.
29. **Что изменилось бы для production?** Добавил бы реальную банковскую интеграцию, авторизацию операций, секреты из надёжного хранилища, логи, пагинацию, проверил бы нагрузку и несколько workers. HMAC, миграции и защита конкурентного изменения статуса уже есть.
30. **Почему архитектура простая?** Семь маршрутов и две таблицы находятся в небольших файлах моделей, схем, БД, подписи и API. Общая функция изменения статуса предотвращает дублирование между вебхуком и рефандом.
